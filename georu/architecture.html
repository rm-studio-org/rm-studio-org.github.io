시스템 아키텍처System architecture

Georu 와 Georu 로 만든 이관 앱이 무엇으로 이뤄져 있고, 무엇과 연결되며, 어떤 계층으로 나뉘는지 설명합니다. 고객 아키텍트 · IT 운영 · 보안 담당과 수행팀(PM · 이관 리더 · 개발자)을 위한 문서입니다.What Georu and a migration app built on it are made of, what they connect to, and how they are layered. Written for client architects, IT operations and security staff, and delivery teams (PM · migration lead · developers).

1시스템 구성도System configuration

Georu 는 데이터 이관 프레임워크입니다. 라이브러리 묶음(jar 모듈 7개)으로 배포되며, 업체는 이를 의존성으로 넣어 이관 앱을 만듭니다. 실행 흐름은 Georu 가 쥐고, 업체가 쓴 이관 코드(SQL · 변환)를 정해진 자리에서 부릅니다. 이관 앱이 소스 DB 를 읽어 타겟 DB 에 씁니다.Georu is a data migration framework. It ships as a library bundle (seven jar modules), and vendors add it as a dependency to build a migration app. Georu owns the execution flow and calls the vendor's migration code (SQL · transformations) at defined points. The migration app reads the source DB and writes to the target DB.

1.2 구성 원칙1.2 Principles

1×1

앱 하나 · 서버 1대One app · one server

이관 실행은 시스템 전체에서 한 번에 하나. 이중화하지 않습니다. 동시 실행이 만드는 채번 충돌과 부하 사고를 구조로 없앱니다.Only one migration runs at a time, system-wide, with no redundancy. Numbering collisions and load accidents from concurrent runs are removed by design.

SQL

규칙은 업체 코드Rules live in vendor code

변환은 Source SQL, Processor 는 검증 · 옮겨 담기. 엔진 내부는 쓰지 않습니다.Transformations go in Source SQL; Processors validate and copy values. Engine internals are never touched.

LOG

기록은 따로Records kept separately

운영 저장소는 타겟과 다른 DB · 스키마입니다. 타겟을 정리해도 이관 이력은 남습니다.The operations store is a different DB · schema from the target, so history survives any target cleanup.

⇄

어디서든 실행Runs anywhere

같은 앱을 로컬 · 도커 · 서버에서 돌립니다. 바뀌는 것은 프로파일과 접속 정보뿐입니다.The same app runs locally, on Docker or on a server; only the profile and connection details change.

2시스템 연관도System context

이관 앱은 DB 와만 붙습니다. 외부 업무 시스템(ERP · EAI · IAM · SSO)과의 연계는 없으므로, 보안 검토 범위는 사용자 채널(HTTP) · DB 연결(JDBC) · 선택적 텔레그램 알림(HTTPS) 세 갈래로 좁혀집니다.The migration app connects only to databases. There is no integration with external business systems (ERP · EAI · IAM · SSO), so the security review narrows to three paths: user channels (HTTP), DB connections (JDBC) and optional Telegram notifications (HTTPS).

2.3 데이터 흐름 (테이블 하나)2.3 Data flow (one table)

  1. 요청 → 실행 게이트Request → execution gate화면 · API · 스케줄에서 요청이 오면 다른 실행이 없는지 먼저 확인합니다.A request from a screen, the API or a schedule first confirms that nothing else is running.
  2. 사전 검사 → 실행 전 점검Pre-run checks → precheckNORMAL 이면 자동 실행 전 점검을 돕니다 — 타겟 메타 · 소스 샘플 SELECT 만, 쓰지 않습니다.For NORMAL, the automatic precheck runs — target metadata and a source sample SELECT only; nothing is written.
  3. 읽기 → 변환 → 큐 → 적재Read → transform → queue → load소스에서 페이지를 읽어 변환하고, 큐를 거쳐 적재 스레드가 타겟에 배치 INSERT 합니다.Pages are read from the source and transformed; load threads take them off the queue and batch-INSERT into the target.
  4. 청크마다 기록Record per chunk진행 · 건수 · 오류를 운영 저장소에 남깁니다.Progress, counts and errors go to the operations store.
  5. 건수 판정 → 알림 · 보고서Count verdict → alerts · reports끝나면 소스 = 타겟 건수를 판정하고 알림 · 보고서를 만듭니다.At the end, source = target count is verified and alerts · reports are produced.

3프레임워크 기능 구성Framework features

Georu 는 기반 프레임워크(Spring Boot · Spring Batch) 위에 만든 데이터 이관 프레임워크입니다. Georu 가 직접 만든 기능과, 그 아래에서 쓰는 기반 프레임워크 · 라이브러리를 나눠 봅니다.Georu is a data migration framework built on base frameworks (Spring Boot · Spring Batch). Below, the features Georu itself provides are separated from the base frameworks · libraries it uses.
