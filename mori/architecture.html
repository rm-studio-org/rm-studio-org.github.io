아키텍처Architecture

MORI 는 기존 보안 · 모니터링 도구와 Grafana / Loki 사이에 놓이는 증적 층입니다. 이 페이지는 MORI 가 어디에 놓이고, 무엇으로 이뤄져 있으며, 데이터가 어떻게 흐르고, 증적의 무결성을 어떻게 지키는지 설명합니다.MORI is an evidence layer that sits between your existing security · monitoring tools and Grafana / Loki. This page explains where it sits, what it is made of, how data flows, and how evidence integrity is protected.

MORI SOC 0.6.0FastAPI · PostgreSQL 16단일 테넌트 · 셀프호스트Single-tenant · self-hosted

1MORI 의 위치Where MORI sits

MORI 는 아무것도 대체하지 않습니다. 소스 도구는 신호를 만들고, Grafana / Loki 는 시계열과 로그를 보여 줍니다. MORI 는 그 사이에서 판단 · 기록 · 증명 — 트리아지 → 조치 → 통제 매핑 → 증적 PDF → 감사 로그 — 을 맡습니다.MORI replaces nothing. Source tools produce signals and Grafana / Loki show time series and logs. MORI handles judgement · records · proof in between — triage → action → control mapping → evidence PDF → audit log.

읽기 전용 원칙Read-only principle

MORI 는 명시적으로 켜지 않는 한 소스 시스템에 쓰지 않습니다. 유일한 예외는 옵트인 · 감사되는 Zabbix write-back 이며, MORI_ZABBIX_WRITEBACK_ENABLED=true 일 때만 동작합니다.MORI never writes to source systems unless you explicitly enable it. The only exception is the opt-in, audited Zabbix write-back, active only with MORI_ZABBIX_WRITEBACK_ENABLED=true.

RO

read-only 토큰 권장Read-only tokens

소스 연결에는 읽기 전용 토큰을 권장하고, 기존 시스템 설정은 바꾸지 않습니다.Read-only tokens are recommended, and existing system settings are never changed.

⛑

소스 장애 격리Source failure isolation

한 소스가 실패해도 나머지는 계속 돕니다. 마지막 수집 시각과 실패 사유를 저장하고 신선도를 표시합니다.One failing source doesn't stop the rest. Last collection time and failure reason are stored and freshness is shown.

AI

AI 금지선AI guardrails

자동 패치 · 자동 예외 승인 · 자동 인시던트 종결은 하지 않습니다. LLM 결과는 항상 초안 / 사람 검토 필요로 표시됩니다.No auto-patching, auto-approved exceptions or auto-closed incidents. LLM output is always marked draft / needs human review.

3데이터 흐름Data flow

3.1 수집 — pull 폴러3.1 Collection — pull pollers

mori-worker 가 소스별 주기로 가져옵니다. 여러 워커가 떠도 PostgreSQL advisory lock 으로 하나만 리더가 됩니다. POST /assets/refresh 로 즉시 수집할 수도 있습니다.mori-worker pulls each source on its own interval; with several workers, a PostgreSQL advisory lock elects a single leader. POST /assets/refresh triggers collection on demand.

Rate limits and caps on body size (10 MB default) and findings (20,000 default) apply.

3.3 읽기 · 쓰기 경로3.3 Read · write path

MORI_QUERY_BACKEND=postgres 이면 요청마다 PostgreSQL 에서 스냅샷을 만들어 워커가 넣은 데이터가 API 재시작 없이 바로 보입니다. UI 운영 상태는 PostgreSQL 에 write-through 되어 재시작 후에도 유지됩니다. 요청마다 전체를 읽는 구조라 대규모 성능은 아직 벤치마크하지 않았고, 옵트인 MORI_QUERY_CACHE_TTL 로 완화할 수 있습니다.With MORI_QUERY_BACKEND=postgres, each request materializes a PostgreSQL snapshot, so worker data appears without restarting the API. UI operational state writes through to PostgreSQL and survives restarts. Because each request reads the full snapshot, large-scale performance is not yet benchmarked; the opt-in MORI_QUERY_CACHE_TTL mitigates it.

4데이터 모델Data model

스키마는 schema/001 ~ 023 으로 관리되고 부팅마다 멱등하게 적용됩니다(이력 · checksum 은 schema_migrations). 운영자의 판단 층(B · C)은 하드 FK 대신 업무 키로 원천 데이터와 연결되어, 재수집해도 사람의 판단이 지워지지 않습니다.The schema is managed as schema/001–023 and applied idempotently on every boot (history and checksums in schema_migrations). Operator-judgement layers (B · C) link to source data by business key rather than hard FKs, so re-collection never erases human decisions.

5인증 · 권한Authentication · roles

세션 쿠키(mori_session, HttpOnly · SameSite=Lax)로 로그인하며, 유휴 8시간 · 절대 7일 뒤 만료됩니다. LDAP 이 켜져 있으면 LDAP 을 먼저, 그다음 로컬 계정을 확인합니다. 반복 실패 시 계정이 잠깁니다(기본 5회 · 15분).Sign-in uses a session cookie (mori_session, HttpOnly · SameSite=Lax) that expires after 8 h idle or 7 days absolute. With LDAP enabled, LDAP is tried before local accounts. Repeated failures lock the account (5 attempts · 15 min by default).

6증적 무결성Evidence integrity

감사 증적은 나중에 바뀌지 않았다는 걸 보여 줄 수 있어야 합니다. MORI 는 다음 장치를 겹쳐 씁니다. 다만 이것은 변조를 드러내는(tamper-evident) 장치이며, 저장소 수준의 WORM 불변성은 아닙니다.Audit evidence must show it hasn't changed after the fact. MORI layers the mechanisms below. They are tamper-evident, not storage-level WORM immutability.

  1. 감사로그 hash chainAudit-log hash chain행동 감사로그는 append-only 이고 각 행이 앞 행의 해시를 담습니다. 수정 · 삭제 API 가 없고, GET /admin/audit-log/verify 로 검증합니다.The action audit log is append-only with each row carrying the previous hash. There is no edit · delete API; verify with GET /admin/audit-log/verify.
  2. 거버넌스 이벤트 원장Governance event ledger통제 운영 변경도 hash chain 원장에 쌓이며 GET /governance/events/verify 로 변조 · 삭제 · 재배열을 감지합니다.Governance changes go to a hash-chained ledger; GET /governance/events/verify detects tampering, deletion or reordering.
  3. content hash · PDF SHA-256Content hash · PDF SHA-256승격된 증적마다 SHA-256 content hash 와 버전이 붙고, 승인 시 증적 집합의 해시와 PDF SHA-256 이 불변 스냅샷으로 고정됩니다.Each promoted record carries a SHA-256 content hash and version; on approval, the set hash and the PDF SHA-256 are frozen in an immutable snapshot.
  4. OIDC provenanceOIDC provenanceGitHub Actions OIDC 토큰의 repository · sha · run_id 를 RS256 으로 검증해 자기신고 값을 덮어씁니다. issuer · audience · 만료 · 저장소 허용목록 · 재사용(jti)을 확인합니다.Verifies repository · sha · run_id from the GitHub Actions OIDC token (RS256) and overrides self-reported values. Checks issuer · audience · expiry · repo allowlist · replay (jti).
  5. 서명된 증적 번들Signed evidence bundleZIP 에 파일별 SHA-256 과 번들 해시를 담은 MANIFEST.json 이 들어가고, MORI_EVIDENCE_SIGNING_KEY 가 있으면 HMAC-SHA256 으로 서명됩니다.ZIPs include a MANIFEST.json with per-file SHA-256 and a bundle hash, HMAC-SHA256 signed when MORI_EVIDENCE_SIGNING_KEY is set.
  6. 기준일 재현 (as-of)As-of replayappend-only 이력을 재생해 감사 기준일의 통제 · 운영주기 상태를 그대로 복원합니다.Replays append-only history to restore control and cycle state as of an audit date.
